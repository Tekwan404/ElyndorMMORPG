# World PvP: фундамент и последовательность внедрения

Дата: 2026-10-17. Статус: первый вертикальный срез в PR, атаки игроков **не включены**.

## Принятый мир

Действующий источник истины — `docs/source-of-truth/gameplay/04_WORLD_AND_LOCATIONS_SYSTEM.md`:

- HUMAN: BORDERLANDS 1–40; UNDEAD: DEAD_KINGDOMS 1–40;
- OUTER_REACHES 41–60 — общая PvE-карта обеих рас;
- только `DEAD_REACHES` (уровень 60) зарезервирована под World PvP;
- арена, группы, городские сервисы и прочие локации не меняются.

Планы дополнительных континентов — отдельное продуктовое решение, не часть этого PR.

## Первый срез: безопасная зона допуска и сигнал в интерфейсе

- `WorldPvpRules` содержит серверный допуск к будущим нападениям.
- Вход: **серверные** снимки CharacterId, AccountId, расы, уровня, локации,
  жизненного состояния и путешествия. Ни одно из полей не принимается как
  доверенное доказательство из клиентского запроса.
- Допуск: оба персонажа — разные аккаунты и разные CharacterId, фракции
  HUMAN/UNDEAD противоположны, оба 60 уровня, оба живы, не путешествуют
  и находятся в одной локации `DEAD_REACHES`.
- Правило само по себе не начинает бой: отсутствие API нападения гарантирует,
  что непроверенная боевка не появится в production через этот PR.
- Bootstrap и каталог локаций отдают `isWorldPvpZone`, вычисленный сервером.
  Фронтенд показывает обозначение спорной зоны и честно предупреждает, что
  нападения ещё недоступны. В остальных регионах такого статуса нет.

Изменение поля `isWorldPvpZone` не является разрешением инициировать PvP.
Боевой endpoint будущего этапа **обязан** повторно выполнять проверки и
проверять реальную серверную локацию обоих игроков.

## Следующие независимые срезы

### 2. Дуэль фракций в `DEAD_REACHES` (только свободные персонажи)

- Серверный поиск доступных вражеских целей без раскрытия скрытых данных.
- Команда нападения с idempotency key, rate limiting и проверкой участников
  по БД внутри защиты от гонок.
- Использование существующей PvP-механики `ArenaCombatSession` там, где она
  применима; не подменять PvP-цель PvE-монстром.
- Один активный бой на каждого персонажа, понятные `404/403/409`, reconnect.
- Никакой чести, жетонов или списания предметов до отдельного settlement-среза.

### 3. `ContestedEncounter` — вторжение в активное PvE

- Изучить `CombatSessionGate`, `CombatSessionRegistry`,
  `ActiveCombatSession`, `CombatSessionFinalizer`, `ArenaCombatSession`.
- Не запускать вторую параллельную сессию для персонажа или монстра.
- Single-writer по session ID; атомарное admission двух сторон и одного
  encounter; разные PvE и PvP правила target/ally/heal.
- Поддержать PvE multi-enemy, companion ownership, Party snapshots, threat
  для монстров, DoT после смерти и смену целей.
- Проверить смерть, бегство, reconnection, restart, disconnect и
  одновременное присоединение нескольких игроков.
- Не разрешать чужой фракции вступать в нормальную Party.
- Первое ограничение: не более двух игроков на каждую фракцию в сессии.

### 4. Честь и награды

- Использовать существующий Arena Honor осторожно: единые или раздельные
  кошельки решить до миграции, не создавать несогласованный баланс.
- Уникальный ключ награды `(combat_id, character_id, reward_kind)`.
- Начисление атомарно с записью settlement; повторная доставка не платит
  повторно, сбой транзакции не оставляет частичную выдачу.
- Credit за damage/heal/defense считать по зафиксированным участникам.
- Протоколировать контекст убийства и повторные пары, антифарм —
  ограничение повторной награды за одну жертву, без наказания по одному IP.
- Баланс 20 чести, 1–3 жетона и сезонные награды — **проектные значения**,
  не производственная конфигурация.

### 5. Розыск, контракты, территории и сезоны

Отдельные PR после подтверждения корректности первых четырёх этапов.
Розыск показывает только приблизительный район цели. Захват территории и
групповое PvP не должны обходить admission и защищённый reward settlement.
Лидерборды — производная проекция, не источник истины.

## Verification / запреты

- Политика: unit tests для противоположных фракций, уровней, чужих регионов,
  себя, второго персонажа своего аккаунта, dead/travel, unknown race.
- UI: тест наличия предупреждения только при серверном флаге.
- Обязательные перед включением боёв: реальные endpoint, integration tests
  для гонок, PostgreSQL уникальных ограничений, безопасный shutdown/restart,
  повторные награды, frontend tests, content validation и CI.
- Нельзя включать призывы «Напасть», выдачу чести или PvPvE по одному лишь
  признаку `isWorldPvpZone`. Дальнейшая логика должна отдельно разрешать
  бой на сервере.

## Failure boundaries

1. Устаревший location snapshot → отклонение команды после перечитывания БД.
2. Два нападения на одного героя → только один admission.
3. Travel/AFK/active encounter → решение с authoritative state под lock.
4. Разрыв связи → reattach к существующей сессии, без дублирования reward.
5. Повторный settlement → нулевая повторная выплата.
6. Атака в PvE-зоне → отказ даже при подделанном клиентском PvP-флаге.
